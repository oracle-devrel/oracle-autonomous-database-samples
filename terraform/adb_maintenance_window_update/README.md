# Terraform — Update an Autonomous Database Serverless Maintenance Window

Updates the recurring maintenance window of an existing ADB-S. Follows the file layout and API-key authentication style of the repository's `adb_ocpu_to_ecpu_update` example.

## Files

| File | Description |
|---|---|
| `main.tf` | Existing ADB resource, declarative import and target window |
| `variables.tf` | Configurable parameters and basic input validation |
| `outputs.tf` | Current and pending maintenance details |
| `versions.tf` | Terraform >= 1.5 and OCI provider pinned to 9.12.1 |
| `provider.tf` | OCI API-key authentication |
| `terraform.tfvars` | Placeholder values to replace |
| `list_windows.py` | Read-only helper to query available windows using the OCI Python SDK |
| `.terraform.lock.hcl` | Provider dependency lock generated by Terraform |

## Prerequisites

- An existing eligible ADB-S: ECPU, Regular patch level, not Always Free or Developer.
- OCI permissions to read and update the database, plus an API signing key.
- Terraform >= 1.5; Python and the OCI Python SDK only for the optional discovery helper.
- A maintenance window returned for this database by `ListAvailableMaintenanceWindows`. Copy the exact day, UTC start/end times and availability domain. The example Sunday window is not guaranteed to exist.

Changing the window can involve movement to another availability domain. Oracle documents a synchronized copy and a brief service interruption when the change is applied. With local Data Guard, the standby may also need to move. Capacity determines whether the requested change succeeds.

## Quick Start

1. Discover available windows. The helper uses your OCI SDK configuration (independent of Terraform credentials), and handles pagination:

   ```bash
   python3 -m pip install oci
   python3 list_windows.py --adb-id '<ADB_OCID>' --region '<OCI_REGION>'
   ```

   Optional arguments: `--config-file ~/.oci/config --profile DEFAULT`.

2. Edit `terraform.tfvars`. Keep `compartment_ocid` and `adb_db_name` equal to the database's current values. Copy a returned window into the four maintenance variables.

3. Initialize and validate:

   ```bash
   terraform init
   terraform fmt -check
   terraform validate
   ```

4. Create and review a plan:

   ```bash
   terraform plan -out=maintenance-window.tfplan
   terraform show maintenance-window.tfplan
   ```

   The `import` block adopts the existing OCID on first apply. Expect an import plus an in-place maintenance-window update, not a new database. Inspect every planned field; do not apply if the plan changes unrelated configuration. The lifecycle rule prevents destruction/replacement while this configuration remains present.

5. Apply the reviewed plan:

   ```bash
   terraform apply maintenance-window.tfplan
   terraform output
   ```

6. Monitor the OCI work request and read the database again after completion. A pending schedule does not by itself prove that the window has changed. Refresh outputs when needed with `terraform apply -refresh-only` after reviewing its plan.

## Existing Terraform ownership

If another Terraform project already owns this database, integrate the maintenance block and variables into that project. Do not import the same database into two independently maintained states. In that case, omit this sample's import block and retain your project's existing resource address, credentials and configuration.

The example deliberately omits passwords and compute/storage settings. It manages an imported database, not provisioning. Review the imported plan because provider defaults and the existing resource configuration can still affect the diff. Keep real variable values, state and plan files out of public repositories; state/plan files may contain sensitive information.

## Scope and limitations

This revised example sends `scheduled_maintenance_window` to `UpdateAutonomousDatabase`. The original active-window block was rejected by OCI with `400 InvalidParameter: Active Maintenance Window cannot be scheduled`. This revision is a proposed correction based on the distinct scheduled-window API field; live service acceptance remains unverified. It does not set a custom execution date, change Early/Regular patch level, or implement cancellation/rescheduling. The provider also exposes scheduled-window fields, but their end-to-end scheduling semantics are not demonstrated here.

The provider documentation still contains legacy wording about cloning to change a window, although the field is marked Updatable and the provider's update implementation sends it to OCI. Local format/schema validation does not establish service acceptance. A successful live plan/apply against an eligible test database remains necessary before treating this as an end-to-end tested sample.
